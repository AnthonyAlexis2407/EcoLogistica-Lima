## 1. Evaluación de Alternativas Tecnológicas

Cada alternativa describe una combinación completa (backend + frontend + base de datos) evaluada bajo 8 criterios, escala 1 (bajo) a 5 (alto).

| Criterio | Alternativa 1: MERN (Node/Express + React + MongoDB) | Alternativa 2: Python/FastAPI + React + PostgreSQL | Alternativa 3: Java Spring Boot + Angular + PostgreSQL |
|---|---|---|---|
| **Curva de aprendizaje** | 5 (JavaScript unificado en todo el stack) | 4 (Python en backend, JS/TS en frontend; equipo ya conoce Python) | 2 (verboso, fuertemente tipado, mayor tiempo de configuración) |
| **Costo** | 4 (infraestructura moderada, Node async I/O) | 5 (FastAPI asíncrono, bajo consumo de RAM, licencias open-source) | 3 (mayor consumo de memoria por JVM, más recursos de cómputo) |
| **Soporte** | 5 (comunidad masiva, gran cantidad de librerías) | 4 (comunidad amplia y en crecimiento acelerado, especialmente en ciencia de datos) | 5 (soporte corporativo consolidado) |
| **Eficiencia energética** | 3 (media) | 5 (alto rendimiento por watt en cargas asíncronas de I/O) | 2 (warm-up de JVM prolongado, mayor consumo en reposo) |
| **Rendimiento** (idoneidad para metaheurísticas GA/Tabú) | 2 (ecosistema numérico limitado, requeriría microservicio externo) | 5 (NumPy, DEAP, OR-Tools y NetworkX nativos del ecosistema) | 3 (librerías de optimización existen pero con menor adopción académica) |
| **Integración** (mapas, geoespacial, APIs externas) | 3 (soporte geoespacial vía librerías de terceros sobre MongoDB) | 5 (PostgreSQL + extensión PostGIS de primera clase; SDKs maduros para Google Maps/OSM) | 4 (PostgreSQL + PostGIS disponible, pero mayor sobrecarga de configuración) |
| **Escalabilidad** | 4 (horizontal, ampliamente probado en producción) | 4 (auto-scaling horizontal sencillo con contenedores + Uvicorn/Gunicorn) | 4 (probado en entornos empresariales de gran escala) |
| **Madurez** | 5 (stack consolidado desde hace más de una década) | 4 (FastAPI es más reciente que Django/Flask, pero su núcleo — Python, Starlette, Pydantic — es maduro) | 5 (ecosistema empresarial muy maduro) |
| **Puntaje total (0-40)** | 31 | **36** | 28 |

## 2. Justificación Técnica Formal

Se selecciona la **Alternativa 2: Python (FastAPI) + React + PostgreSQL**, en concordancia con la restricción tecnológica R03 del Documento 04 (Registro de Supuestos y Restricciones: "Tecnologías: Python, React, PostgreSQL") y con el mayor puntaje ponderado obtenido en la matriz anterior.

La decisión se sustenta en tres ejes:

1. **Rendimiento del núcleo algorítmico:** el motor de optimización (VRPTW + Green VRP) requiere iteración numérica intensiva bajo el límite de 45 segundos (RNF-001). El ecosistema Python permite implementar y comparar metaheurísticas (Algoritmos Genéticos con DEAP, Búsqueda Tabú propia, o resolución híbrida con Google OR-Tools) sin salir del mismo lenguaje del backend, reduciendo la complejidad de integración frente a un microservicio separado en otro lenguaje.

2. **Perfil e idoneidad del equipo:** los tres integrantes cubren roles de Backend, Frontend/PM y Base de Datos. Python + FastAPI tiene una curva de adopción razonable para consolidar el backend y el módulo de optimización en un solo repositorio, mientras React se mantiene como frontend desacoplado vía REST/JSON, consistente con la experiencia previa del equipo.

3. **Eficiencia energética y costo en la nube:** dado que la sostenibilidad es un pilar central del proyecto (Documento 13, dimensión "Cero Carbono Neto"), FastAPI sobre un servidor ASGI asíncrono (Uvicorn/Gunicorn) reduce el uso de CPU por petición frente a la JVM, y PostgreSQL con PostGIS evita la necesidad de una base de datos geoespacial adicional, disminuyendo tanto el costo de infraestructura (R01) como la huella de carbono operativa (RNF-009).
